# M2-C1 — verified first-party transfer publication

Scope: both existing user-initiated LSPosed Downloads routes (stable GitHub release APK/ZIP and first-party CI evidence ZIP). This is the publication/cancellation foundation of M2-C, not completion of M2 or M3. Preserve the M1-C Activity journal, the existing receipt schemas, legacy hash-only listing, exact release and Actions identities, CI evidence-only extraction, and every Vector authorization boundary. No APK installation, root action, background download, new source catalogue or release qualification is introduced.

- Verify the selected stable release tag, exact uploaded asset, length, digest and URL before transfer and again before new publication. CI rechecks exact run/attempt/artifact before transfer and after transfer. Credentials remain confined to the API connection; storage redirects never receive a token. Refuse malformed or stale metadata instead of claiming verified results.
- Identity-encoded full responses are bounded by the expected size. Reject a wrong Content-Length, zero, short, extra, invalid or stalled-read bytes. Preserve route-specific maximum sizes. Hash the entire staged file and the final file using the pinned Shared bounded SHA-256 primitive; keep existing format admission and CI ZIP inspection. Reserve sufficient available storage before staging.
- A single shared app-owned publication path creates a unique same-directory pending file, flushes file bytes, atomically hard-links the verified file without replacing any destination, syncs the directory, and publishes a unique, flushed receipt by another non-replacing link. The receipt is the visibility boundary. Unsupported safe publication fails closed rather than falling back to an overwriting rename. Parent aliases used by Android Context paths are allowed; the actual storage directory and files must not be symlinks. Existing exact bytes and exact receipts may be reused; conflicts, including legacy receipts that cannot truthfully be relabelled, are preserved and refused. No attempt deletes a final destination. A complete orphan without a receipt is not surfaced; explicit retry after fresh metadata may rehash and reconcile it. Pending staging names are not downloadable results.
- Only an explicit cancellation signal produces CANCELLED. A timeout is a failure. Check cancellation before and after reads and just before publication, but do not abort a committed publication halfway through its receipt. Report success only after final byte/receipt read-back and Activity terminal persistence. Errors returned to the UI contain controlled descriptions, not network URLs, credentials or exception messages. UI progress remains below 100 until publication succeeds and updates from both routes are bounded and dispatched onto the UI coroutine.

Local standalone Kotlin cases exercise real bounded streaming and real filesystem operations, including conflict, cancellation, timeout, tampering, receipt collision, orphan reconciliation, symlink, and concurrent writers. Hosted JUnit runs the same cases; release metadata negative controls run using the project's actual JSON implementation. Hosted Android CI, R4D, emulator and physical API 26+ storage/receipt testing remain separate acceptance requirements. No local Gradle. M2-C queue, retry scheduling, safe resume and persistent per-item controls and M3-C sources/catalogue remain later work.
